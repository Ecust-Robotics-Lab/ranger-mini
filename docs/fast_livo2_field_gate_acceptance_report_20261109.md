## 当前具体问题

### 采集交付停顿与同步积压

在第一次LOST附近：原始LiDAR最大接收间隔约0.103秒，保持连续；相机raw图像出现0.528744秒接收间隔，image_sync出现0.527230秒间隔；FAST位姿/区间云出现约0.6587秒间隔。C1最后确认年龄到0.5118秒时失效，符合现有新鲜度规则。

相机CSV更具体：设备帧号539→540连续，设备tick差与单帧正常间隔相近，而主机取帧记录从6839439940918到6839967362885ns，间隔0.527422秒。随后541–544帧在短时间积压送达，读取同一份共享scan时间1122，四帧被记为BACKWARD而未发image_sync。最终922帧中918同步成功、4帧BACKWARD。时序吻合“主机取得图像迟到、之后积压帧无法获得独立scan时间”的问题。

不能据此断定相机物理曝光停止、SDK等待、网络重传或线程调度哪一个是唯一根因。实际LIO/VIO日志内部计时最大分别17.244ms/9.937ms，不能用这些局部计时解释完整0.66秒输出停顿；现有日志也不足以完全排除发布阻塞。下一项应离线分解取帧等待、同步取时、发布及前端等待的时延，而非重跑同类90秒来碰运气。

### 恢复可用性

失效后虽自动恢复，但约34秒的恢复等待还不适合宣称成熟连续导航通过。期间导航就绪应撤销，实车自动控制只能按既有失效策略停留，不能继续使用过期地图修正。

另有29条“私有定位仍有效时wheel不新鲜”的桥接诊断，以及首次/恢复对齐窗口的短暂未就绪，均保留在统计中，不宣称所有公共时序问题彻底消失。已有证据优先排查采集迟到及回调交付，而不是放宽过期门限。
