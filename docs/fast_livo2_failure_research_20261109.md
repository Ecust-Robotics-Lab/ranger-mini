# 相机交付停顿与重定位恢复慢：网络检索及本机复核

日期：2026-11-09。范围：按用户要求搜索官方资料、只读分析88k5eclm原包/CSV/源码并提出方案。未实施运行逻辑修复、未启动设备、未改参数/系统、未提交/推送；既有未提交改动保留。现场连续就绪仍PARTIAL。

## 结论与新增证据

两个问题相互放大：相机交付迟到后，旧图读到最新scan时间；C1确认过期后，节点丢弃局部跟踪状态并走全局搜索。全局搜索大量候选不能通过粗配准，短暂输入中断遂变成长时间不可用。不能将34秒全部归因于small_gicp计算慢。

原始bag的完整estimate消息比`localization_samples.jsonl`观察器更完整，本轮统计采用原始SQLite只读反序列化。心跳仍可能覆盖两次发布间的短暂搜索结果，因此下列是已观察到的结果，不是全部求解调用数，也不能计算地点检索precision/recall。

## 问题一：交付停顿及图像时间关联

1. 帧539→540设备帧号连续，设备tick增加约9999954，与邻帧一致；主机取帧返回间隔527.422ms。随后541–544在约24ms内陆续取出，说明存在交付积压，不支持直接认定曝光停止。
2. 帧539的共享scan为1112，帧540为1122，scan时间前进约499.68ms，而设备仅前进一帧。相对正常一帧进度，多出约0.4秒。540仍标为OK，541–544因复用1122被记为BACKWARD。**单调检查拦住后四帧，却未拦住第一张迟到旧图被赋予新scan时间。** 约0.4秒是相对时序错配证据，不是曝光中心的绝对标定结果。
3. 539从取帧返回至sync publish返回只有7.851ms；停顿主要落在其publish返回之后、540取帧返回之前约519.571ms。按归档源码，此区间包括CSV写入/flush、线程调度和下一次SDK取帧等待。故不能将这一具体停顿直接认定为539图像DDS发布阻塞。540的对应处理耗时10.387ms。
4. 驱动采集、转RGB、raw发布、读取最新共享scan、sync发布和CSV逐帧flush在同一线程；SDK缓存8帧，未显式选择抓取策略。本机海康MVS官方头文件确认默认OneByOne，支持LatestImages/LatestImagesOnly，Linux USB可用。仅增大缓存会保留更多过期图像，不能修复关联。
5. 当前raw/sync均RELIABLE、depth5。Fast DDS官方说明RELIABLE在资源限制触发时可能阻塞write；它是应测的其他延迟来源，现有证据不足以认定本次根因。相机为USB3，GigE重传/MTU优化不适用。

建议按小改动顺序实施：

- 补SDK调用前后、转换前后、两次发布前后、CSV写入前后计时，使用内存汇总/批量日志，避免新诊断逐帧刷盘。离线可检查关联逻辑，真实SDK/USB等待仍需以后一次有目标的采集才能区分。
- 分离取帧与发布/日志，用有限队列；正常帧及时处理，积压按明确策略处理。评估LatestImages（输出1–2帧），但不能只切该参数后继续把任意旧图贴上最新scan戳。
- 利用设备帧号、设备tick增量、scan序列历史建立同次会话关联。启动阶段建立相位，掉帧/积压按序列识别；先做最小修正：无法可靠关联的迟到图像拒绝，不冒充当前图像。若补历史ring，可为仍有对应scan的图像使用对应时间。保持已有+100ms前端相位语义，不能重复补偿；不能用接收now或固定10Hz倒推当作真实曝光标定。
- 单独对照实时图像best_effort小队列与现有RELIABLE，核对前端、录包器全部QoS兼容，按采集完整性与端到端延迟决定。writer、IMU等不做全链路盲改。SDK/USB的URB、缓存、控制器竞争仅在计时指向它时检查，不先修改系统参数。

## 问题二：短时丢失后重新冷启动

`node.cpp`在确认样本年龄超过0.5秒时使就绪无效，并入队Reset。工作线程重建Localizer、reset Relocalizer，下一扫描进入无初值全局搜索。这把“最新位姿暂不可用”和“上一有效地点信息已完全失效”合并处理，缺少短时中断恢复路径。

后续39轮已观察失败的主体是粗配准未收敛/内点不足，并非small_gicp耗时。为何粗配准失败仍有两个待区分原因：v2是否漏掉正确区域，以及正确区域即使入选，2帧查询/点稀疏/视角差和目标采样是否不足以形成30内点。无独立真值，不能先断言检索错误或KISS算法不合适。还观察到运动支持门槛等待；丢失后自动停车时，强制0.15m或0.08rad的新运动会使恢复更困难。

首选增加**仅显式C2模式启用的局部恢复**：

1. 过期立刻撤销就绪，但保留上一已验证地图位姿和对应FAST本地位姿作为内部候选，不发布为当前有效修正。
2. 同一前端会话、时钟连续、短时中断且局部里程计增量合理时，在新鲜云到达后计算`X_pred(t)=X_valid(t0)*inverse(U(t0))*U(t)`，在上一地点周边用small_gicp几何重验。所有U、X必须对应实际采样时刻；不通过latest TF拼接。
3. 新鲜几何结果通过残差、重叠、退化、创新及多帧一致性后才恢复就绪；局部恢复不应机械要求车辆先移动0.15m。静止多帧不等于新的独立全局证据，它依赖此前已验证的地点先验，必须单独标识和测试。
4. 超出短时/运动范围、前端身份变化或局部匹配失败，退回既有v2→KISS→small_gicp→C1。独立C1人工初值语义保持不变；不实施前端自动重启或滤波器恢复。

后续优化两处：

- 全局召回：用现有包的失效段比较正确区域是否在top5；先检验top10并作空间去重，再检验2帧与5–8帧运动补偿局部查询、体素均匀采样和点数。分开实验，不同时堆参数。已确认轨迹只能作参考标签，不能冒充真值。粗配准29内点与30内点的硬切值得离线验证，可研究让低置信粗解进入严格精配准，但不能直接降低最终通过标准。
- C1交接：同一子图/查询的KD树、协方差、降采样结果复用，减少13初值的重复预处理。small_gicp官方提供此接口；保留几何检查和必要的歧义验证，避免每个初值都从向量重新建数据。优先实现局部恢复，冷启动优化次之。

## 最短实施与验收顺序

先修相机时间关联并增加分段计时，同时实现C2局部恢复；然后用原包保留接收延迟的重放和0.3/0.6/1秒中断注入检验。只按header重排回放会抹去现场迟到，不能作为此故障复现。原数据不改，诊断关联视图另存，不追认物理同步。

目标：明确拒绝迟到错配图像；同会话短时故障在首个新鲜配对恢复后约1–2秒内重新就绪（工程目标，尚未实现/验收）；静止也能恢复；错误先验、前端重置、错地图不得靠保留状态放行。完成后再补一次带分段计时的短测检查真实SDK/USB。不必先更换检索器、关闭图像、扩大0.5秒有效门限或推倒当前定位链路。
